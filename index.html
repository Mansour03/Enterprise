    What is ArcGIS Enterprise?

    إيه هو ArcGIS Enterprise

    ArcGIS Enterprise هو النظام الأساسي اللي بيشغّل الـ GIS جوه المؤسسة بتاعتك: بيربط الناس بالداتا، وبيدّيهم mapping وvisualization وanalytics وdata management من المتصفح والموبايل، وكل ده على infrastructure انت اللي بتتحكم فيها (on-premises أو private cloud أو public cloud). الصفحة دي شرح كامل لصفحة Esri الرسمية "What is ArcGIS Enterprise?" (الإصدار 12.1 على Windows وLinux)، بالعامية، ومعاها سيناريوهات حقيقية وأمثلة من شغلك.

    إزاي تقرأ الصفحة

    كل section هنا بيشرح جزء من الصفحة الرسمية بالترتيب، وبعدين بنضيف "إيه معنى ده عمليًا؟" على Windows. الأجزاء اللي عليها علامة سيناريو واقعي أمثلة توضيحية من عندنا مش من الـ documentation. الرسمة التفاعلية في قسم الـ base deployment تقدر تضغط على كل component وتتابع الطلب خطوة بخطوة.

    Overview

    Esri بتعرّف ArcGIS Enterprise بإنه "the foundational software system for GIS". يعني هو الأساس اللي باقي الأدوات واقفة عليه. وظيفته الأساسية تربط المستخدمين بالداتا، وتدّيهم أدوات للـ:

    • Mapping وvisualization: خرائط ومشاهد 2D/3D بتتعمل وتتشارك من المتصفح.
    • Analytics: تحليل مكاني (spatial analysis) على السيرفر مش على جهازك.
    • Data management: تخزين الداتا وإدارتها وتحديثها بشكل مركزي.

    وبيشتغل مع ArcGIS Pro (تنشر منه لـ Enterprise وتفتح منه المحتوى)، وممكن يتوصل بـ ArcGIS Online علشان المحتوى يتشارك بين النظامين (هنشرح ده في الصفحة التانية).

    أنا بشتغل بـ ArcGIS Pro، يبقى إيه الفرق؟

    ArcGIS Pro برنامج desktop: انت بتشتغل عليه لوحدك على جهازك، وبتعدّل الداتا وتحللها. المشكلة إن زملاءك (الـ surveying، الـ QC، الـ technical office، المدير) مش هيفتحوا Pro ولا هيشوفوا شغلك. Enterprise بيحل ده: بتنشر الداتا كـ web layers وبتبني عليها web maps وdashboards وapps، والكل يفتحها بـ link.

    سيناريو واقعي (مثال توضيحي): تقاطعات مرورية

    عندك 12 تقاطع تحت التنفيذ. من غير نظام مركزي: كل قسم عنده Excel وملف CAD وخريطة PDF بتتبعت بالإيميل، ولما المساح يحدّث حاجة محدش يعرف إنها اتحدثت. مع Enterprise: الـ feature layer بتاع "نسب الإنجاز لكل تقاطع" منشورة مرة واحدة، المساح بيحدّثها من الموبايل بـ Field Maps، والـ dashboard بتاع الإدارة بيتحدث لوحده، وإنت ما بتبعتش ملف لحد.

    The Web GIS idea

    علشان تفهم أي حاجة في Enterprise لازم تفهم الـ pattern الأساسي (اسمه Web GIS): الداتا بتتحول لـ services، والـ services بتتجمع في خرائط، والخرائط بتتفتح في تطبيقات.

    AuthorArcGIS Pro: تجهّز الداتا وتنسّق الـ symbology

    PublishShare as web layer على الـ Portal

    كل خطوة هنا بتتم على component مختلف من الـ Enterprise، وده بالظبط اللي هنشرحه في الأقسام الجاية. لو فهمت مين بيعمل إيه، هتعرف تحل أي مشكلة وانت بتدوّر على السبب في الطبقة الصح.

    What you can do with it

    الصفحة الرسمية بتقول إن Enterprise بيفتح لك إمكانيات متقدمة حسب الـ servers اللي بتركّبها:

    Real-time data tracking
    تتابع داتا لحظية: عربيات، sensors، كاميرات. مثال: متابعة معدات الموقع أو حساسات المرور.
    Big data analysis
    تحليل بيانات ضخمة (ملايين السجلات) بشكل distributed بدل ما تعلّق جهازك.
    Raster analytics
    معالجة صور وrasters كبيرة على السيرفر (فروقات ارتفاعات، تغيّر، classification).
    Image service hosting
    استضافة الصور الجوية وorthomosaics من الدرون كـ services تتفتح من أي مكان.
    Data science workflows
    تشغّل Python notebooks وmachine learning على المنصة نفسها.
    Disaster recovery / HA
    تضبط النظام بحيث لو machine وقعت ما تضيعش داتا ولا يحصل downtime.

    Deployment flexibility

    أهم نقطة تميّز Enterprise: انت اللي بتختار فين وإزاي يتركّب.

    • الأماكن: public cloud (AWS/Azure)، private cloud، أو on-premises على سيرفراتك أو virtual machines.
    • الحجم: من machine واحدة (للتجربة أو الفرق الصغيرة) لحد multi-machine كبيرة فيها redundancy.
    • الأنظمة: الصفحة بتتكلم عن Enterprise على Windows وLinux (فيه نسخة تانية على Kubernetes بتصميم مختلف، وهي برا نطاق صفحتنا).
    • الوصول: من أي جهاز، في أي وقت، حسب ما Esri بتقول "work anywhere, anytime".
    على Windows

    على Windows الـ Web Adaptor بيتركّب على IIS، والـ components بتشتغل كـ Windows services، والـ authentication ممكن يتربط بـ Active Directory. ده بيخلي Windows اختيار طبيعي لو الشركة أصلاً على Microsoft stack. ملحوظة مهمة من Esri: الـ Web Adaptor مش لازم يكون على نفس نظام التشغيل بتاع الـ component، يعني Windows portal ممكن يستخدم Java Web Adaptor على Linux والعكس.

    The base deployment: four core components

    الصفحة الرسمية بتقول إن Enterprise مبني على أربع مكونات أساسية. لما بيتركّبوا ويتظبطوا مع بعض بنسميه base ArcGIS Enterprise deployment.

    Portal for ArcGIS

    المخزن المركزي لمعلومات المؤسسة والمشاركة: الـ items والـ users والـ groups والـ roles، ومنه بتفتح Map Viewer والـ Content.

    ArcGIS Server

    اللي بيشغّل الـ mapping والـ analysis عن طريق server roles مختلفة، وبيتوسع (scale) ديناميكيًا حسب الحمل.

    ArcGIS Data Store

    بنية التخزين اللي الـ hosting server بيعتمد عليها (relational, object, ...).

    ArcGIS Web Adaptor

    بيربط الـ Enterprise بالـ web server الموجود عندك وبنظام الـ security بتاع المؤسسة.

    التعريف الرسمي للـ base deployment بالظبط

    • Portal for ArcGIS متضبط كـ portal ومرخّص بـ user types وuser type extensions والـ add-on apps.
    • ArcGIS Server مرخّص كـ GIS Server ومتضبط كـ hosting server.
    • ArcGIS Data Store متضبط كـ relational store.
    • Object store بيتوفر إما من ArcGIS Data Store أو من cloud storage مدعوم.
    • اتنين Web Adaptors: واحد للـ portal وواحد للـ hosting server، أو load balancer من طرف تالت.

    جرّب بنفسك: Architecture Explorer

    اضغط على أي مربع علشان تقرا دوره، أو استخدم أزرار الـ stepper تحت علشان تتابع طلب مستخدم حقيقي من المتصفح لحد الداتا.

    ليه محتاج الـ Web Adaptor أصلاً؟

    الصفحة الرسمية للـ Web Adaptor بتقول صراحة إنك ما تقدرش تنشر Portal for ArcGIS من غير Web Adaptor أو تقنية مكافئة (reverse proxy / load balancer بيعمل forwarding وsecurity). الأسباب العملية:

    • بيخبي الـ infrastructure: بدل https://gisserver:6443/arcgis/rest/services الناس بتشوف https://gis.company.com/server/rest/services. ما حدش بيشوف port 6443 ولا الاسم الداخلي arcgis.
    • بيقفل الـ Admin: الـ Administrator Directory والـ Manager مش بيبقوا متاحين من بره.
    • نقطة دخول واحدة: لو عندك أكتر من machine الـ Web Adaptor بيوزّع الطلبات على الشغالة بس.
    • Security على مستوى الـ web tier: تربط الـ identity store والـ policies بتاعت المؤسسة، وPKI client certificates لو الـ web server بيدعمها.
    قاعدة لازم تحفظها

    الـ Web Adaptor version لازم يطابق version الـ component اللي متظبط معاه دايمًا. لو عملت patch أو upgrade للـ Portal ونسيت الـ Web Adaptor، هتلاقي الـ registration أو الـ requests بتفشل بأخطاء غريبة. ودايمًا استخدم DNS alias مش hostname المباشر، علشان لو نقلت السيرفر يوم ما، الـ URL يفضل زي ما هو.

    REST serviceshttps://gisserver:6443/arcgis/rest/serviceshttps://gis.company.com/server/rest/services

    المثال مبني على أنماط الـ URL في صفحة Esri الرسمية للـ Web Adaptor. الأسماء portal وserver وgis.company.com اختياراتنا نحن.

    أنماط التركيب: machine واحدة، multi-machine، HA

    Single machine
    كل الـ components على سيرفر واحد، وبتتركّب بـ ArcGIS Enterprise Builder، وEsri بتقول إنها بتخلص "في أقل من ساعة". مناسبة للـ dev/test وللفرق الصغيرة والـ proof of concept.
    Multi-machine
    الـ components موزعة على أكتر من سيرفر. Esri بتوفر ArcGIS Chef Cookbooks لأتمتة التركيب. بتتوسع لما الحمل يزيد (تضيف ArcGIS Server machines للـ hosting site، خصوصًا لو الـ spatial analysis تقيل).
    Highly available
    كل component ليه redundancy علشان لو machine أو أكتر وقعت، النظام يفضل شغال بأقل downtime.
    سيناريو واقعي (مثال توضيحي): من إيه تبدأ؟

    شركة مقاولات عندها 25 مستخدم GIS وCAD ومشاريع كتير. أنسب بداية: machine واحدة قوية على Windows Server (VM) بـ Enterprise Builder للـ dev/test الأول، تجرّب فيها كل الـ workflow (publish, Field Maps, dashboards). لما الفريق يعتمد عليها فعلاً تنتقل لـ multi-machine (Portal وServer منفصلين، والـ Data Store على machine لوحده) وبعدين تضيف HA لما الـ downtime يبقى مكلف. أرقام الـ hardware بتيجي من Esri system requirements مش من تخمينا.

    ArcGIS Server-based servers

    ArcGIS Server مش بس "GIS Server". من خلاله (لما يكون مرخّص ومعمول له federate مع الـ Portal) تقدر تركّب أنواع تانية من الـ servers:

    Serverبيعمل إيهمثال من شغلنا
    GIS Serverبيستضيف map وfeature وgeoprocessing services. هو الأساس، وبيتضبط كـ hosting server.نشر طبقات التقاطعات وشبكة تصريف الأمطار.
    GeoEnrichment Serverإثراء الداتا بمعلومات إضافية (demographics وغيرها) من داتا المؤسسة.إضافة كثافة سكانية للمناطق حوالين التقاطعات.
    Image Serverraster analytics واستضافة image services.orthomosaic من درون لمتابعة تقدم أعمال الطريق.
    Knowledge Serverknowledge graphs: ربط كيانات وعلاقات معقدة.ربط الأصول بالعقود والمقاولين والمخالفات.
    Workflow Manager Serverأتمتة العمليات وأوامر الشغل.مسار اعتماد تعديلات التصميم بين الأقسام.

    الفكرة إن كل role بيتفعّل بترخيص مناسب وبيتعمله federate مع الـ Portal، وبعدها بيظهر في الـ Portal كـ server بدور محدد.

    Additional capability-based servers

    دي بتتركّب بعمليات تركيب منفصلة (installers مستقلة) مش من خلال ArcGIS Server العادي:

    Data Pipelines Server
    بناء pipelines لسحب الداتا وتحويلها وتحميلها (ETL) بدون كود كتير.
    GeoEvent Server
    معالجة real-time streams (IoT, AVL, sensors) وتنبيهات لحظية. مثال: حساسات حركة المرور أو تتبع عربيات الموقع.
    Mission Server
    دعم عمليات الـ mission والـ situational awareness.
    Notebook Server
    تشغيل Python notebooks جوه المنصة. مناسب جدًا لو بتبني automation بـ arcpy وAPI for Python.
    Video Server
    استضافة وبث الفيديو والـ motion imagery. مثال: كاميرات مراقبة أو فيديو درون.
    Velocity
    معالجة الداتا اللحظية والـ big data. الصفحة الرسمية بتحطه ضمن الـ capability-based servers؛ راجع documentation الإصدار بتاعك لتفاصيل تركيبه.

    Applications and licensing

    الـ Enterprise بيوسّع استخدام الخرائط وتطبيقات الـ GIS جوه المؤسسة عن طريق app frameworks جاهزة: Map Viewer، Dashboards، Experience Builder، Field Maps، Survey123، QuickCapture وغيرها. أهم نقطة إنها كلها بتتعامل مع نفس الـ Portal ونفس الـ services، فالداتا واحدة والتطبيقات كتير.

    الترخيص: اتنين أبعاد

    Esri بتقول إن الترخيص شغال على نموذجين مع بعض:

    1. على مستوى المستخدم (named users): كل مستخدم له user type بيحدد الأدوات اللي يقدر يوصلها.
    2. على مستوى السعة (system capacity): قدرة النظام نفسه على الشغل.

    وأنواع المستخدمين (حسب صفحة Esri الخاصة بيها):

    User typeيقدر يعمل إيه
    Viewerيشوف المحتوى المتشارك معاه واستخدام تطبيقات محددة. مفيش إنشاء ولا تعديل.
    Contributorيشوف ويعدّل الداتا في الخرائط والتطبيقات المتشاركة. مفيش analysis ولا إنشاء.
    Mobile Workerيجمّع ويعدّل داتا في الميدان ويشارك موقعه ويسجّل track. مناسب لتطبيقات الميدان.
    Creatorينشئ ويعدّل خرائط وتطبيقات ويعمل spatial analysis. معاه ArcGIS Pro Basic.
    Professionalمعاه ArcGIS Pro Standard + Advanced Editing extension.
    Professional Plusمعاه ArcGIS Pro Advanced + Advanced Editing extension. للمحللين المتقدمين والمطورين.

    وفيه add-on licenses (زي Business Analyst) بتتوزع على مستخدمين محددين بس. وزي ما شفت في تعريف الـ base deployment، الـ Portal بيتـ license بـ user types وuser type extensions وadd-on apps.

    سيناريو واقعي (مثال توضيحي): توزيع الـ user types

    فريق مشروع تقاطعات: انت (GIS specialist) Professional أو Professional Plus علشان بتشتغل على Pro وتعمل scripting. المساحين Mobile Worker بيجمّعوا الداتا بـ Field Maps. مدير الجودة Contributor لو بيراجع ويعدّل attributes. المدير العام والـ client Viewer بيشوفوا الـ dashboard بس. التوزيع ده بيوفر تكلفة كبيرة مقارنة إن الكل ياخد Creator.

    Key takeaways

    • Enterprise هو نظام الـ Web GIS الأساسي اللي بتشغّله على infrastructure بتتحكم فيها، وبيتكامل مع Pro وبيتوصل بـ ArcGIS Online.
    • الـ base deployment = Portal + ArcGIS Server (hosting) + Data Store (relational) + object store + Web Adaptors.
    • الـ Web Adaptor إلزامي للـ Portal ولازم يطابق الـ version، وبيخبي الـ ports والـ admin interfaces.
    • تقدر تبدأ بـ machine واحدة (Enterprise Builder) وتكبر لـ multi-machine وبعدين HA.
    • فيه ثلاث طبقات servers: ArcGIS Server-based، extensions، وcapability-based servers بتتركّب منفصلة.
    • الترخيص = named users بـ user types + system capacity.
    Choosing a platform

    ArcGIS Online vs Enterprise

    الفرق والاختيار بينهم

    السؤال اللي بيتسأل في كل مشروع: نستخدم ArcGIS Online ولا ArcGIS Enterprise؟ الصفحة دي شرح كامل لصفحة Esri الرسمية "Understand the relationship between ArcGIS Enterprise and ArcGIS Online". الإجابة مش "ده أحسن من ده"؛ الاتنين بيعملوا نفس الشغل الأساسي، لكن في بيئتين مختلفتين، واختيارك بيتوقف على مين بيشغّل الـ infrastructure، وفين الداتا، وإيه التحليلات اللي محتاجها.

    Overview: نفس الفكرة، بيئتين مختلفتين

    Esri بتقول إن الاتنين بيوفروا قدرات على مستوى المؤسسة: mapping وanalysis وdata management وsharing وcollaboration. الفرق الجوهري هو أين وإزاي بيشتغلوا:

    ArcGIS Online SaaS

    مستضاف على سيرفرات Esri. كل حاجة (التحديثات والـ scaling والـ maintenance) على Esri. انت محتاج subscription للمؤسسة بس.

    ArcGIS Enterprise Self-managed

    برنامج بتركّبه انت على infrastructure بتتحكم فيها (cloud أو on-premises أو VMs). انت اللي بتحدّث وتعمل patching وbackup.

    تشبيه سريع: ArcGIS Online زي ما تأجّر مكتب جاهز بخدمة كاملة، وEnterprise زي ما تبني مكتبك بنفسك: تتحكم في كل تفصيلة، بس مسؤول عن الصيانة.

    What they share

    قبل الفروق، لازم تعرف إن كتير جدًا مشترك، وده بيسهّل الانتقال أو الدمج بينهم:

    • موقع مركزي بيسمح للمستخدمين ينشئوا ويخصصوا ويحللوا ويشاركوا داتا وخرائط 2D و3D.
    • الوصول لمجموعة تطبيقات Esri المكتبية والميدانية (Dashboards, Field Maps, Survey123...).
    • الوصول لـ ArcGIS Living Atlas of the World (الداتا الجغرافية الجاهزة).
    • واجهات administrator ويب متشابهة لتخصيص المؤسسة.
    • نفس الـ APIs والـ SDKs للمطورين: يعني الكود اللي بتكتبه بـ ArcGIS API for Python أو JavaScript شغال على الاتنين بتغييرات بسيطة (غالبًا الـ URL بس).
    مهم لتعلّمك كـ developer

    بما إن الـ APIs واحدة، تقدر تتعلم وتجرّب كل حاجة على ArcGIS Online، وبعدين تنقل نفس السكربتات لـ Enterprise. ده يوفر عليك وقت كبير.

    The major differences

    1) Deployment model: مين بيشغّل إيه

    ArcGIS Online
    SaaS مستضاف على سيرفرات Esri. Esri بتدير التحديثات والـ scaling والـ maintenance. التحديثات بتنزل حوالي 3 مرات في السنة. محتاج subscription للمؤسسة بس.
    ArcGIS Enterprise
    برنامج بتركّبه على infrastructure انت بتتحكم فيها: cloud أو on-premises أو virtual machines. بيتيح تصميمات "highly customized"، وبيدعم high availability وdisaster recovery والنشر المنفصل عن الإنترنت. فيه إصدار أو اتنين في السنة، وانت اللي بتتحكم في توقيت الـ patching والـ upgrade.
    سيناريو واقعي (مثال توضيحي): التحديثات

    مشروع حكومي بيتسلّم بعد 3 شهور وفيه dashboard معتمدة من الـ client. على ArcGIS Online، تحديث من Esri ممكن يغيّر شكل أو سلوك أداة من غير ما تختار الوقت. على Enterprise انت بتأجّل الـ upgrade لحد ما تخلص التسليم وتختبره على بيئة staging. ده فرق يهم المشاريع اللي فيها اعتمادات رسمية.

    2) Advanced capabilities: القدرات المتقدمة

    على Enterprise القدرات المتقدمة بتجي عن طريق capability-based servers بتركّبها (راجع الصفحة الأولى). على ArcGIS Online فيه منتجات مقابلة جاهزة:

    القدرةعلى Enterpriseعلى ArcGIS Online
    Image / raster processingImage Server (raster analytics + hosting)ArcGIS Image
    Big data + real-timeGeoEvent Server / Velocity / big data capabilitiesArcGIS Velocity
    Scripting (Python)Notebook ServerArcGIS Notebooks
    Data science, knowledge graphs, alertingservers مخصصة تركّبها وتديرهاحسب المنتجات المتاحة في الـ subscription

    3) Data management: الفرق الأهم

    الصفحة الرسمية بتوصفه بإنه Critical Distinction:

    • Enterprise بيتوصل بمخازن داتا انت بتديرها (cloud storage، folders، databases). الناشر ينشر "by reference" يعني الداتا تفضل في مكانها.
    • ArcGIS Online بيتطلب نسخ الداتا جوه النظام المستضاف، أو استخدام distributed collaboration.
    سيناريو واقعي (مثال توضيحي): شبكة تصريف في Enterprise geodatabase

    عندك شبكة مياه أمطار في enterprise geodatabase (SQL Server أو PostgreSQL) وفيها editing وversioning ومئات آلاف الـ features وفرق بتعدّل عليها. على Enterprise: بتسجّل الـ geodatabase على الـ federated server وتنشر referenced layers، والداتا ما بتتحركش من قاعدة البيانات. على ArcGIS Online: لازم تنسخ الداتا للـ hosted layers وتدير المزامنة، وده مش دايمًا مناسب لداتا حية وكبيرة. تفاصيل hosted vs referenced هنشرحها في موضوع الـ data storage لاحقًا.

    4) مميزات إضافية في Enterprise

    • Custom geocode services وgeoprocessing services: تنشر الـ locators وأدوات الـ geoprocessing بتاعتك كخدمات.
    • Enhanced security: web-tier authentication، وتكامل مع Active Directory.

    5) الـ authentication المشتركة

    الاتنين بيدعموا SAML وOpenID Connect وMulti-Factor Authentication. يعني ما تعتبرش إن Enterprise هو الوحيد اللي يقدر يتكامل مع identity provider بتاع الشركة.

    Using both: distributed collaboration

    الصفحة الرسمية بتقول إن مؤسسات كتير بتستخدم الاتنين مع بعض عن طريق distributed collaboration: بتشارك layers وmaps وdata بين النظامين. وبيدعموا unified credentials، لكن كل واحد ليه organization ومخزن محتوى منفصل.

    Guest
    المؤسسة المدعوة: بتقبل الدعوة وتنضم لـ groups وتضبط الـ synchronization.

    feature layers (referenced وcopied)، maps، apps، items. الـ feature layers بتدعم تعديل في الاتجاهين، فالداتا اللي اتجمعت في الميدان ترجع للنظام الأصلي.
    Collaboration badge

    سيناريوهات الاستخدام (من الصفحة الرسمية)

    • مؤسستين: قسمين (زي التخطيط وتنمية المجتمع) كل واحد عنده Enterprise خاص بيه ويتشاركوا.
    • مؤسسة مركزية + أقسام: مدينة عندها Enterprise رئيسي بالداتا المعتمدة، والأقسام guests بتساهم بداتا تشغيلية بجدول sync.
    • Online + Enterprise: جهة حكومية بتتواصل مع المواطنين عن طريق ArcGIS Online، والأقسام عندها Enterprise داخلي، فبلاغات الحوادث بتتتبع لحظيًا.
    • عمليات ميدانية: جمع داتا offline بـ Field Maps ومزامنتها في الاتجاهين بين Enterprise وOnline.
    سيناريو واقعي (مثال توضيحي): بلاغات المواطنين

    جهة عندها Enterprise داخلي فيه الداتا المعتمدة (طرق، تقاطعات، أصول). عايزة المواطنين يبلّغوا عن حفرة أو إشارة معطلة. بدل ما تفتح الـ Enterprise للإنترنت، بتعمل Survey123 على ArcGIS Online (واجهة عامة)، وبـ distributed collaboration البلاغات بتتزامن لـ Enterprise بجدول زمني، والمهندسين بيعالجوها من جوه الشبكة الداخلية. المواطن ما شافش الداتا الداخلية، والداتا الحساسة ما خرجتش.

    When to choose ArcGIS Enterprise

    Esri بتقول اختار Enterprise لما تحتاج:

    • تحكم كامل في الـ infrastructure.
    • Data residency: متطلبات إن الداتا تتخزن في موقعك (on-site).
    • بيئة بدون إنترنت أو إنترنت غير مستقر.
    • تحليلات متقدمة وmعالجة موزعة (distributed processing).

    وقيّم العوامل دي قبل ما تقرر:

    التحكم والـ SLA
    عايز تتحكم في الـ infrastructure والـ service level agreements ولا تسيبها لـ Esri؟
    مكان المستخدمين
    المستخدمين فين؟ داخل الشبكة، برا، موبايل، مقاولين؟
    نوع التحليل
    أي analysis محتاجها وفين لازم تتنفذ؟
    تكامل الداتا
    داتا من مخازنك الداخلية ولا استضافة Esri؟
    سؤال لازم تسأله للـ client

    في مشاريع كتير فيها جهات حكومية، بيكون فيه متطلبات خاصة بمكان تخزين الداتا والأمن السيبراني. اسأل الـ IT/security بتاع الـ client بشكل صريح: هل مسموح الداتا تتخزن على cloud خارج بنيتهم؟ الإجابة دي لوحدها بتحسم الاختيار في أغلب الأحيان.

    Key takeaways

    • الاتنين بيوفروا mapping وanalysis وdata management وsharing وcollaboration، بنفس الـ APIs والـ SDKs.

    User workflows

    الشغل اللي المستخدمين هيعملوه هو اللي بيحدد القدرات (capabilities) اللي محتاجها. النقاط اللي Esri بتذكرها:

    • الـ base deployment بيدعم mapping وfeature analysis واستضافة التطبيقات (application hosting).
    • لو محتاج حاجة زي raster analysis أو maritime mapping متخصص، ممكن تحتاج server roles إضافية أو server extensions.
    • الـ workflows المختلفة ممكن تحتاج تراخيص مختلفة، فتأكد إن عندك العدد والنوع الصح من الـ licenses.

    ربط الكلام ده بالصفحات اللي جاية: لو الـ workflow بتاعك "نشر طبقات وعمل dashboards وجمع داتا ميداني" يبقى الـ base deployment كفاية. لو بتتكلم عن "معالجة صور درون" يبقى محتاج Image Server. لو محتاج "network routing" يبقى ده extension مش role.

    System scale

    الـ ArcGIS Enterprise بيقدر يتعامل مع حجم كبير جدًا من الطلبات على الخرائط والتطبيقات والـ services. لكن في المقابل: كل ما الطلبات تزيد، لازم موارد حسابية (computing resources) أكتر، وده بيأثر على تصميم الـ deployment. الفكرة إنك تخطط لطلب المستخدمين من خلال الـ architecture وتكوين الـ services.

    • الـ scale الكبير ممكن يميل بيك لـ cloud deployment لأنه بيوفر services قابلة للتوسع وvirtual machines بتتجهز بسرعة.
    • لو محتاج أعلى درجات الـ scalability، الصفحة بتشير إن Kubernetes (ArcGIS Enterprise on Kubernetes) ممكن يكون الأنسب. ده منتج بتصميم مختلف عن الـ Windows/Linux اللي بنشرحه هنا.

    أسئلة لتقدير الـ scale

    السؤالليه بيفرق
    كام مستخدم هيفتحوا الخرائط في نفس الوقت (concurrent)؟الـ concurrency هو اللي بيحدد عدد الـ service instances والـ machines، مش عدد الـ accounts.
    هل في طبقات عامة بتتفتح من الإنترنت (public)؟ممكن تيجي موجات طلبات مفاجئة؛ ده بيدفع لـ cloud أو caching أو load balancing.
    حجم الداتا (آلاف ولا ملايين features)؟بيحدد نوع التخزين (hosted ولا referenced من geodatabase) وأداء الـ queries.
    هل هتعمل spatial analysis تقيل؟الـ analysis بتستهلك CPU وmemory كتير على الـ hosting server site (هنشرحها في صفحة الـ base deployment).
    فيه مواسم ذروة (تسليمات، حملات)؟تصمم للذروة مش للمتوسط، أو تستخدم cloud علشان تكبّر وتصغّر.
    نصيحة عملية

    الـ scale مش بس hardware. الـ service configuration (عدد instances، caching بـ vector tiles، تبسيط الـ symbology والـ popups، فلترة الداتا) ممكن توفر عليك سيرفر كامل. جرب تحسّن الـ service قبل ما تزوّد الـ hardware.

    Uptime requirements

    الصفحة بتقول بوضوح إن تحمّل التوقف (outage) بيختلف جدًا: فيه مؤسسات تتحمل توقف بعد الضهر، وفيه مؤسسات ما تتحملش 15 دقيقة. فالخطوة الأولى إنك تحدد متطلبات التوقف والاعتماديات التجارية (business dependencies). وقاعدة بسيطة: كل ما تكلفة الـ downtime أعلى، استثمر أكتر في الـ resiliency.

    اللي Esri بتوصي بيه في الجزء ده:

    1. حدد الـ RTO والـ RPO بلغة الشغل

      يعني: "لو النظام وقع، نقبل نستنى كام ساعة؟ ونقبل نخسر داتا آخر كام ساعة؟" الأرقام دي بتحدد إذا كنت محتاج HA كامل ولا backup كويس يكفي.

    2. اعمل استراتيجية لتقليل ضياع الداتا والـ downtime

      ممكن تشمل high availability (redundancy في كل component). في الصفحة اللي بعد كده هنوضح إزاي بتتبني على الـ base deployment.

    3. استخدم بيئات متدرجة (tiered environments)

      development ثم staging ثم production، علشان تختبر أي تغيير قبل ما يوصل للمستخدمين الحقيقيين.

    4. حدد maintenance windows

      الـ patches والـ upgrades أحيانًا بتحتاج توقف. اتفق على نافذة صيانة تحقق التوازن بين احتياج الصيانة وإزعاج المستخدمين، واعلن عنها للمستخدمين.

    سيناريو واقعي (مثال توضيحي): مين بيتضرر لو وقع النظام؟

    الـ dashboard بتاعت المتابعة المرورية بتتفتح في اجتماع أسبوعي، ولو وقعت يوم الاجتماع الدنيا تقف نص ساعة: ده توقف مقبول، وbackup يومي كويس يكفي. لكن لو نفس النظام بيستقبل بلاغات ميدانية من 40 مساح طول اليوم، وتوقف ساعة معناه ضياع شغل ميداني: هنا الـ HA والـ staging مبررين. نفس التقنية، قرارين مختلفين، لأن "كلفة التوقف" مختلفة.

    HA مش بديل للـ backup

    الـ high availability بيحمي من وقوع machine. لكنه ما بيحميش من إنك مسحت layer بالغلط أو من داتا اتخربت، لأن الغلط بيتنسخ للـ standby. محتاج الاتنين: HA للاستمرارية وbackup/DR للاسترجاع.

    Security posture

    سياسات الأمان في المؤسسة بتأثر على حاجتين محددتين حسب الصفحة:

    • إيه حسابات ArcGIS (ArcGIS accounts) اللي هتستخدمها: يعني الحسابات اللي بتشغّل الـ services وتدير الـ site. على Windows ده بيبقى Windows account (غالبًا domain service account) بصلاحيات محسوبة.
    • إزاي بتسمح للـ ports اللي ArcGIS Enterprise محتاجها إنها تتواصل: بين الـ components جوه الشبكة، وبين الـ clients والـ Web Adaptor.

    وكمان بتشكّل best practices الأمان لكل component: Portal for ArcGIS وArcGIS Server وArcGIS Data Store. الصفحة الرسمية بتحيلك لصفحة لكل واحد منهم (هتلاقيها في الـ Resources تحت).

    اسأل الأسئلة دي بدري

    الـ network/security team عادةً هم اللي بيقولوا "لا" في آخر لحظة. اسألهم من الأول: هل مسموح بـ port 443 من برا؟ هل في firewall بين الـ web tier والـ app tier؟ هل الشهادات من CA داخلي ولا عام؟ هل الـ identity provider (Active Directory, SAML) متاح؟ هل في قيود على مكان تخزين الداتا (data residency)؟ كل إجابة بتغيّر التصميم.

    Base ArcGIS Enterprise deployment

    الـ base deployment وأنماطه

    الـ base ArcGIS Enterprise deployment هو الحد الأدنى من النظام اللي يعتبر "ArcGIS Enterprise كامل" وبيدّيك web GIS شغال: خرائط، تحليل features، واستضافة تطبيقات. الصفحة دي شرح لصفحة Esri "Base ArcGIS Enterprise deployment" من زاوية التخطيط: إيه بالظبط جواه، وتركّبه إزاي (machine واحدة، أكتر من machine، أو highly available)، وإزاي يكبر لما الحمل يزيد. لو عايز تعرف دور كل component وإزاي بيتكلموا مع بعض، ارجع للصفحة الأولى؛ هنا تركيزنا على القرارات.

    Overview: إيه اللي جوه الـ base deployment؟

    الصفحة الرسمية بتعرّفه بأنه الحد الأدنى المكوّن من:

    Portal for ArcGIS
    متضبط كـ portal ومرخّص بـ user types وuser type extensions والـ add-on apps.
    ArcGIS Server
    مرخّص كـ ArcGIS GIS Server ومتضبط كـ hosting server.
    ArcGIS Data Store
    متضبط كـ relational store.
    Object store
    بيتوفر من ArcGIS Data Store أو من cloud storage service مدعومة.
    ArcGIS Web Adaptor
    اتنين: واحد مضبوط مع الـ portal وواحد مع الـ hosting server. أو بدلهم load balancer من طرف تالت.

    والمكونات دي ممكن تتركّب على machine واحدة أو أكتر، سواء physical أو virtual أو cloud. مواصفات الـ machines مكتوبة في صفحة الـ system requirements الرسمية للـ Enterprise (مش في صفحة الـ base deployment).

    نقطة بتلخبط ناس كتير

    الـ GIS Server هنا له دورين في نفس الوقت: هو الـ hosting server (اللي بيستضيف الـ hosted layers وبيشتغل مع الـ Data Store) ومحتمل يبقى كمان general-purpose server للـ services بتاعتك. في الإنتاج الكبير بيتفصلوا لـ sites منفصلة (هنوضح في صفحة Additional servers).

    ليه كل عنصر موجود؟

    علشان تقدر تخطط، لازم تعرف لو شلت عنصر هيحصل إيه:

    العنصرلو مش موجودملحوظة تخطيطية
    Portalمفيش users وgroups وitems ولا Map Viewer. مفيش web GIS بالمعنى الكامل.بيتـ license بالـ user types، فعدد المستخدمين ونوعهم قرار ميزانية.
    Hosting serverما تقدرش تنشر hosted feature layers ولا تستخدم Survey123 بنفس الطريقة.هو اللي بيتحمل الـ spatial analysis التقيلة، فهو أول مرشح للتوسع.
    Relational storeمفيش مكان تتخزن فيه الـ hosted feature layers.مرتبط بـ backup وDR، وبيتعمل HA بنظام primary/standby.
    Object storeمفيش تخزين لـ 3D hosted layers وresponse cache والفيديو.ممكن يبقى cloud storage بدل Data Store.
    Web Adaptors (اتنين)مفيش نقطة دخول آمنة، والـ ports الداخلية تتكشف.لو عندك load balancer معتمد في الشركة ممكن يحل محلهم.

    Single-machine deployment

    كل الـ components بتشتغل على machine واحدة (all-in-one). Esri بتقول إن أداة ArcGIS Enterprise Builder بتعمل التركيب ده في "أقل من ساعة". ده الأسهل والأسرع، لكن كل حاجة على نقطة فشل واحدة وبتتنافس على نفس الـ CPU والـ memory.

    مناسب لـ
    • بيئة dev/test أو staging.
    • Proof of concept لمشروع قبل ما تلتزم بتصميم كبير.
    • فريق صغير جدًا وحمل خفيف وتوقف مقبول.
    • تعلّم الإدارة (ده أحسن lab ليك على Windows Server VM).
    عيب مهم

    أي analysis تقيلة هتاخد CPU وmemory من الـ Portal والـ Data Store على نفس الجهاز، فممكن المستخدمين العاديين يحسّوا ببطء. وكمان أي patch أو restart بيوقف النظام كله.

    Multimachine deployment

    الـ components بتتوزع على اتنين أو أكتر من الـ machines. Esri بتوفر ArcGIS Chef Cookbooks على GitHub لأتمتة التركيب باستخدام Chef framework. الفايدة: كل component ليه موارده، وتقدر تكبّر اللي محتاج بس.

    سيناريو واقعي (مثال توضيحي): ليه تفصل الـ Data Store؟

    الـ hosted feature layers بتاعت Field Maps بتكتب فيها عشرات المساحين طول اليوم. لو الـ Data Store على نفس الجهاز اللي بيشغّل analysis تقيلة بالليل، الـ I/O والـ memory بيتنافسوا. لما الـ Data Store يبقى على machine مخصصة، أداء الكتابة الميداني بيفضل ثابت، وتقدر تعمل له backup وتراقبه لوحده.

    Highly available deployment

    كل component بيتظبط بـ redundancy علشان لو machine أو أكتر وقعت، يقل الـ downtime. الصفحة بتوضح نقطتين مهمتين:

    • الـ HA ممكن تتعمل على الـ single-machine وعلى الـ multimachine deployment على السواء.
    • الـ Chef Cookbooks ممكن تساعد في أتمتة بناء HA كمان.

    تفاصيل الإعداد في صفحة "Configure highly available ArcGIS Enterprise" الرسمية، وهنغطيها في صفحة HA لاحقًا لما تطلبها. اللي لازم تفهمه دلوقتي: HA معناها إن كل عنصر في الجدول اللي فوق ليه نسخة تانية، وده بيضاعف عدد الـ machines تقريبًا. علشان كده القرار بتاعه بيجي من تقييم الـ uptime.

    إزاي تختار النمط؟

    النمطالمميزاتالعيوبمناسب لـ
    Single machineأسرع وأرخص، Enterprise Builder في أقل من ساعةنقطة فشل واحدة، تنافس على المواردdev/test، POC، فرق صغيرة
    Multimachineموارد منفصلة، توسع انتقائي، Chef automationإدارة أكتر، شبكة بين الـ machinesproduction متوسط
    Highly availableيقلل الـ downtime لو machine وقعتتكلفة وتعقيد أعلى، لازم backup برضهأنظمة ما تتحملش توقف

    Scaling: لما الحمل يزيد

    الصفحة الرسمية بتقول إن مع زيادة المستخدمين والنشاط، ممكن component أو أكتر يحتاج موارد أكتر. وبتحدد حاجة مهمة: أدوات الـ spatial analysis بتستهلك memory وCPU كبيرين على الـ hosting server site. والحل الرسمي لإضافة سعة: تضيف ArcGIS Server machines للـ hosting server site.

    سيناريو واقعي (مثال توضيحي): البطء الأسبوعي

    كل يوم خميس الفريق بيشغّل buffer وoverlay على طبقات كبيرة، والـ dashboard بتبقى بطيئة لكل الناس. التشخيص: الـ analysis بتاكل موارد الـ hosting server الوحيد. الحلول بالترتيب: (1) جدول الـ analysis في وقت هادي، (2) أضف ArcGIS Server machine للـ hosting site، (3) لو الأنماط دي بقت دائمة، افصل analysis وhosting عن الـ production services في sites منفصلة.

    الخلاصة التخطيطية

    ما تقدّرش تحتاج hardware من صفحة الـ base deployment. الصفحة بتقولك صراحة إن مواصفات الـ machines في صفحة system requirements. وبعد التركيب، راقب الـ CPU والـ memory على الـ hosting server علشان تعرف تكبّر امتى.

    ملاحظات Windows للتخطيط

    • الـ Web Adaptor على Windows بيتركّب على IIS، وزي ما اتقال، مش لازم يطابق نظام تشغيل الـ component.
    • لو هتوزع على أكتر من machine على Windows، حضّر الشبكة والـ DNS والـ firewall بين الـ machines قبل التركيب، وحدد الحسابات (service accounts) اللي هتشغّل الـ services.
    • على multimachine، فكّر بدري في مكان الـ shared directories لو الـ site فيها أكتر من machine (ده بيظهر في صفحة التركيب).
    • الـ Enterprise Builder هو أنسب مدخل لـ lab على Windows Server VM قبل ما تصمم الـ production.

    أخطاء شائعة في التخطيط

    تخطي الـ staging

    تركّب وتجرب في production مباشرة. أي patch بعد كده يبقى مغامرة.

    تخمين الـ hardware

    الأرقام لازم تيجي من system requirements الرسمية ومن قياس الحمل الفعلي.

    HA من غير backup

    الـ standby بينسخ الغلط كمان. لازم backup/DR مستقل.

    نسيان الـ Web Adaptors

    اتنين مطلوبين في الـ base deployment، ولازم يطابقوا الـ version.

    Additional server deployment

    الـ servers الإضافية

    الـ base deployment بيدّيك web GIS كامل، لكن لما تحتاج قدرات تانية (صور، real-time، notebooks، فيديو، knowledge graphs...) أو سعة أكبر، بتضيف servers إضافية. صفحة Esri "Additional server deployment" بتقول إن السيرفرات دي، سواء on-premises أو في الـ cloud، بتضيف وظائف وسعة للـ base deployment، وإن لكل نوع إرشاداته الخاصة في التخزين وعدد السيرفرات وحجم الـ site. الصفحة دي بتشرح كل نوع بالتفصيل، ومعاها أداة صغيرة تقولك أنهي servers تحتاجها.

    فكرة أساسية

    في الـ base deployment المستخدمين بيوصلوا لموارد الـ web GIS من خلال المؤسسة (Portal + Web Adaptors)، أما الـ administrators والـ publishers فممكن يوصلوا لـ ArcGIS Server مباشرة. كل server إضافي بيتـ federate مع الـ Portal وبيظهر كـ role، فالمستخدم بيستخدم قدرته من غير ما يعرف فين بتشتغل.

    ArcGIS GIS Server

    في الـ base deployment الـ GIS Server بيستضيف البنية التحتية للـ web GIS (hosted layers وغيرها)، وفي نفس الوقت بيشتغل كـ general-purpose server للـ services اللي مبنية على مصادر داتا بتاعتك زي الـ geodatabases. المشكلة إن الدورين دول بيتنافسوا على نفس الموارد.

    • مؤسسات كتير بتفصل الدورين في site-ين علشان الأداء: site للـ hosting، وsite للـ services بتاعت الداتا الإنتاجية.
    • نمط شائع: site من 3 machines مخصص للـ mapping والـ visualization، وبيتعمل له federate مع الـ Portal. عدد الـ machines بيعتمد على السعة واحتياج الـ HA.
    • كل machine لازم يكون فيها 8 GB memory على الأقل، وأكتر حسب الـ services المنشورة والاستخدام.
    سيناريو واقعي (مثال توضيحي): شبكة تصريف بترسم لـ 200 مستخدم

    شبكة مياه الأمطار referenced من enterprise geodatabase وبتتفتح في خرائط الإدارة طول اليوم، وفي نفس الوقت الفريق بيرفع نتايج الـ Survey123 على الـ hosting server. لو الاتنين على site واحد، رفع داتا تقيل ممكن يبطّأ الخرائط. الحل: site مخصص (3 machines مثلاً) للـ services الإنتاجية المرجعية، وsite الـ hosting يفضل لـ hosted layers والـ analysis.

    ArcGIS Data Pipelines Server

    قدرة no-code وvisual لهندسة البيانات: تجهّز وتدمج الداتا لأغراض الـ mapping والـ analysis. تقدر تضيف machines للـ site لدعم مؤلفين (authors) أكتر أو موارد أكتر لكل author.

    تخيل إنك بتسحب داتا من ملف أو قاعدة بيانات أو cloud، تنضّفها وتدمجها، وتطلعها feature layer جاهزة، كل ده بواجهة رسم من غير ما تكتب سكربت.

    ArcGIS GeoEnrichment Server

    متاح مع ArcGIS Business Analyst Enterprise: حزمة بتجمع بيانات demographic وlifestyle وbehavioral وspending مع location analytics. بتدعم تخطيط الأسواق واختيار المواقع واستهداف العملاء. مش من أدواتك اليومية في مشاريع الطرق، لكن مفيدة لو حللت مواقع خدمات حوالين محاور مرورية.

    ArcGIS GeoEvent Server

    بيدمج real-time event-based data streams من sensors وmobile devices وIoT في الـ GIS المؤسسي. الأرقام اللي بتحدد التصميم (من الصفحة الرسمية):

    البندالقيمة
    Throughput لـ instance واحدة (simple point events)حتى حوالي 6,000 event/ثانية
    Throughput مع complex eventsحوالي 2,000 event/ثانية
    Relational store يكفي لـ streamsأقل من 200 event/ثانية
    للأرشفة العاليةspatiotemporal big data store من 3 nodes
    • الـ throughput بيتوقف على الداتا نفسها، وعلى الـ processors الموجودة في الـ workflow.
    • التوصية كحد أدنى: base deployment + Data Store على machine تانية + GeoEvent site على machine تالتة.
    • التركيب على machine موجودة في الـ base مدعوم، لكن لازم تراعي مشاركة الموارد مع الـ GIS Server قبل الـ production.
    • لو عندك عدة streams متوسطة، الصفحة بتقترح GeoEvent site من machine واحدة لكل stream.
    • GeoEvent sites ما بتستخدمش Web Adaptor. الـ load balancers ممكن توزع داتا الـ sensors لكن غالبًا ما بتدعمش الـ administration.
    سيناريو واقعي (مثال توضيحي): حساسات تقاطع

    20 حساس على تقاطعات بيبعتوا قراءة كل ثانية = 20 event/ثانية، وده رقم صغير جدًا مقارنة بـ 200 اللي الـ relational store بيتحمله. ما تحتاجش big data store. لو بقوا 5000 حساس بقراءات معقدة، التصميم يتغير بالكامل: spatiotemporal big data store وsite مخصص.

    ArcGIS Image Server

    بيوفر dynamic image services من الـ mosaic datasets، وdistributed raster analysis. إرشادات التصميم:

    • لو محتاج dynamic image services بس: أضف Image Server site مخصص، وتقدر تعمل federate لـ sites إضافية.
    • لو بتعمل raster analysis كبيرة بانتظام: استخدم sites منفصلة للـ analysis وللـ dynamic image services، علشان واحد ما يأثرش على التاني. كل machine محتاجة 8 GB RAM على الأقل.
    • Image Server site واحد فقط ممكن يتخصص للـ raster analytics. توسّعه بـ RAM أو machines أكتر.
    سيناريو واقعي (مثال توضيحي): صور درون لمتابعة الطريق

    درون بيصوّر مشروع طريق كل أسبوع، فبيطلع orthomosaic حجمه GBs. بتستضيفه كـ image service على Image Server علشان الفريق والـ client يفتحوه في الخريطة. ولو عايز تحسب فرق الارتفاعات أو تعمل classification، دي raster analytics على الـ site المخصص، مش على الـ site اللي بيخدم الـ image service للناس.

    ArcGIS Knowledge Server

    بيمثّل العلاقات بين الكيانات باستخدام knowledge graph layers. لو هتعمل federate له لازم يكون عندك ArcGIS Data Store متضبط كـ graph data store على machine لوحده. وتقدر تضيف machines للـ site لتسريع التحليلات المعقدة.

    مثال: بدل جداول منفصلة للأصول والمقاولين والعقود والمخالفات، بتبني graph يقولك "إيه كل الأصول المرتبطة بالمقاول ده، وإيه المخالفات اللي عليها؟" بشكل مرئي.

    ArcGIS Mission Server

    بيسهّل الاتصال بين التحديثات الميدانية اللحظية وغرفة القيادة (command center) لدعم إدارة المهام واتخاذ القرار. يهمك لو شغلك عمليات ميدانية منسقة (طوارئ، أحداث كبيرة).

    ArcGIS Notebook Server

    منصة data science لتشغيل ArcGIS Notebooks بـ Python: تحليل مكاني، machine learning، data management، وأتمتة المهام الإدارية. أهم نقاطه التقنية:

    • بيتـ configure وfederate مع الـ deployment، وWeb Adaptor لكل site.
    • بيستخدم Docker containers لعزل بيئة كل author. لازم Docker Engine يتركّب على نفس الـ machine.
    • أضف machines للـ site لعدد authors أكتر أو workspaces أكبر.
    ليه ده يهمك كـ GIS developer

    عندك أصلاً سكربتات arcpy كتير. Notebook Server بيخليك تشغّلها على السيرفر بدل جهازك، وتجدولها (مثلاً فحص جودة يومي)، وتشاركها كـ notebooks للفريق. ده انتقال طبيعي من "سكربت على جهازي" لـ "automation مركزي".

    Windows

    الصفحة بتقول Docker Engine لازم يتركّب على نفس الـ machine. راجع صفحة Notebook Server الرسمية للإصدار بتاعك علشان تعرف دعم الـ containers على Windows بالظبط قبل ما تخطط له.

    ArcGIS Reality Server (beta)

    بيوفر computing وstorage موزع لعمل reality mapping من صور الدرون والجوية والأقمار الصناعية. النمط الموصى بيه: image hosting site مخصص + Reality Server site متعدد الـ machines، والاتنين بـ raster store. ده بيمنع إن المعالجة تتنافس مع استضافة الصور. لاحظ إن الصفحة بتوصفه beta.

    ArcGIS Velocity Server

    قدرة الـ real-time والـ big data: بتستورد وتعرض وتحلل وتخزّن داتا IoT sensors، وبتفلتر وتوجّه الأحداث عالية السرعة، وبتفعّل تنبيهات، وبتدعم analytic models.

    ArcGIS Video Server

    بيفهرس وبيبحث وبينشر وبيبث الفيديو كـ geospatial, temporal video services للتطبيقات. بيتعمل له federate مع Web Adaptor لكل site، وممكن يشتغل على machine لوحده أو على machine الـ hosting server. بعد الـ federation بتحدد الـ site كـ Video Server role.

    مثال: فيديو درون أو كاميرات مراقبة لمنطقة تنفيذ بتتعامل معاه كطبقة خريطة، تضغط على نقطة وتشوف الفيديو الزمني بتاعها.

    ArcGIS Workflow Manager Server

    نظام workflow management قابل للتوسع مع web app مدمج لشغل GIS وغير GIS. بيتعمل federate مع Web Adaptor، وممكن يشتغل على machine لوحده أو على machine الـ hosting server. مثال: مسار اعتماد تعديل تصميم يمر على قسم التصميم ثم الـ QC ثم الـ technical office، وكل مرحلة ليها مسؤول وحالة.

    Server extensions

    الـ extensions والـ editions

    الـ server extensions هي إضافات بتوسّع قدرات ArcGIS GIS Server: تنشر بيها تحليلات ونطاقات تخصصية (network routing، raster analysis، جودة الداتا، linear referencing للطرق...). صفحة Esri "Server extensions" بتشرح إن الـ GIS Server بيوفر mapping وanalytics وdata management في Enterprise، وبينشر services وبيستضيف layers وبيوفر محتوى Living Atlas وبيدعم OGC web services وgeoprocessing مخصص، وهو مطلوب للـ hosting server. وفوق ده Esri بتقدم extensions كتير ليها نسخة desktop ونسخة server منفصلتين. الصفحة دي شرح لكل ده بالتفصيل مع ربطه بشغلك.

    الفرق بين server role و extension

    الـ server roles (Image Server, Notebook Server...) هي servers مستقلة بتتركّب وتتعمل federate. أما الـ extensions فهي قدرات بتتفعّل على الـ GIS Server نفسه بترخيص مناسب لإصدار الـ GIS Server عندك. السؤال الأول دايمًا: "أنا على أنهي edition؟".

    GIS Server editions

    الإصدار (edition) اللي عندك هو اللي بيحدد إيه المتاح. الصفحة الرسمية بتعرّف تلات editions:

    Editionبيشملقيود مهمة
    Basicإدارة geodatabase، نشر feature services (نشر بس، مش editing)، geometry service، geodata services.ما ينفعش يتعمله federate مع portal ولا يبقى hosting server. مفيش extensions.
    Standardكل اللي في Basic + كل أنواع الـ GIS web services، web editing عن طريق feature services، وgeoprocessing services من أدوات ArcGIS Pro Standard.الـ extensions اختيارية ومتاحة للشراء.

    القدرات المدمجة في Advanced

    Share 3D services and embed 3D analysis tools

    بتوفر أدوات 3D Analyst للأسطح، وإدارة lidar، وتحليلات الرؤية (visibility)، وهندسة الـ 3D features، واستخدام TINs كمصادر ارتفاع. مفيدة لو بتنشر مشاهد 3D وتحليلات sightline (تحليل رؤية السائق للإشارة مثلاً).

    Serve geostatistical models

    بتوفر أدوات Geostatistical Analyst لنماذج الـ interpolation مع cross-validation وdiagnostics تانية. مثال: عمل سطح استيفاء لقياسات ضوضاء أو ضغط أو منسوب مياه من نقاط متفرقة.

    Share/Embed Spatial Analyst tools and services

    بتوفر تحليلات raster وأسطح: slope وaspect وweighted overlay وleast-cost paths. مثال: أنسب مسار لخط خدمات بناءً على الميل واستخدامات الأراضي.

    Network Analyst (Included في Advanced، Purchase في Standard)

    بيوفر routing وdriving directions وservice area وclosest-facility عن طريق web services، وبيسمح بنشر أدوات اتبنت على desktop لتطبيقات desktop وmobile وweb. مثال مباشر في شغلك: تحليل منطقة خدمة خلال 5 دقايق قيادة من مركز طوارئ، أو أقرب موقع صيانة لتقاطع معطّل.

    Extensions بتشتريها لوحدها

    Data Interoperability

    بيشارك أدوات بتتعامل مع صيغ ونماذج داتا كتير. فيه أدوات Spatial ETL بدون كود، وتكاملات ومزامنات آمنة، ونشر workflows متجدولة أو بتتفعل بـ webhook.

    سيناريو واقعي (مثال توضيحي): CAD → GIS كخدمة

    قسم التصميم بيسلّم ملفات DWG أسبوعيًا، وأنت بتحوّلها لـ feature classes وتدخلها الـ geodatabase يدويًا بسكربت. بـ Data Interoperability تبني الـ ETL مرة وتنشره كـ geoprocessing service، والفريق بيرفع الـ DWG ويطلعله النتيجة بدون ما يعتمد عليك. ده يوفر ساعات كل أسبوع.

    Data Reviewer

    بيوفر workflows لجودة الداتا عن طريق web وmobile apps، وبيعلّم تلقائيًا الداتا اللي بتفشل في متطلبات الجودة، وبيعمل تقارير جودة عبر المنصات. ده امتداد طبيعي لشغل قسم الـ QC: checks آلية قبل أي تسليم.

    Roads and Highways

    بيضيف قدرات linear referencing REST لشبكات الطرق (Roads and Highways LRS): نشر الـ LRS networks والـ events، تحديد المسارات والـ measures (locate)، التحقق من القيم (validate)، تحويل الـ measures بين الطرق (convert)، واستخدام widgets الـ LRS في Experience Builder.

    Pipeline Referencing

    نفس فكرة linear referencing REST لكن لشبكات خطوط الأنابيب: نشر LRS networks وevents، locate routes وmeasures، validate، convert، وwidgets Experience Builder.

    Maritime

    بينشر مجموعات بيانات الخرائط البحرية S-57 وS-63 كـ RESTful وOGC WMS services، وبيدعم common operating pictures وCustom Chart Builder لإنتاج خرائط الملاحة. ملحوظة: الـ Custom Chart Builder مش متاح على Linux. على Windows ما فيش القيد ده.

    Aviation Airports

    بيشارك خرائط وgeoprocessing services مبنية على المطارات. بيعمل Obstacle Identification Surfaces كخرائط 2D أو مشاهد 3D وبينشر أدوات obstacle-intersection.

    Aviation Charting

    بيتبادل بيانات الملاحة AIXM 5.1، وبيستورد بيانات العوائق الرقمية من FAA، وبينشر أدوات لأتمتة إنتاج الخرائط الملاحية.

    Topographic Mapping

    بيركّز القواعد الكارتوجرافية والـ templates والـ workflows لإنتاج الخرائط الطبوغرافية بنظام self-service، وفيه web apps لمنتجات الخرائط وjobs الـ workflow. مش متاح للشراء على Standard؛ متاح للشراء على Advanced فقط.

    Workflow Manager Server

    بيظهر في الجدول كـ extension للشراء على Standard وAdvanced، وهو نفسه بيتتركّب كـ server (راجع Additional servers).

    Deployment scenarios

    نظرة عامة والمصطلحات

    صفحة Esri "Deployment scenarios" هي المدخل لمجموعة صفحات بتشرح إزاي تركّب ArcGIS Server site بأحجام وأشكال مختلفة: من machine واحدة للتجربة، لحد pool من الـ machines ورا load balancer للإنتاج الكبير. الصفحة دي بتعرّف المصطلحات (site، web adaptor، reverse proxy، NLB، server directories، configuration store)، وبتوريك خريطة السيناريوهات الأربعة اللي هنشرحها في الصفحات الجاية. افهم المصطلحات هنا كويس، لأن كل الصفحات اللي بعدها بتتبني عليها.

    ازاي الصفحات دي تتربط بالـ Enterprise؟

    السيناريوهات دي بتتكلم عن ArcGIS Server site نفسه، سواء كان federated مع portal أو stand-alone. في الـ Enterprise، الـ hosting server هو site من النوع ده، وأي GIS Server إضافي بتعمله federate هو site كمان. يعني الأنماط دي بتنطبق على كل site في نظامك، ومش بس على الـ hosting server. وتقدر تعمل في deployment واحد أكتر من site، كل واحد بغرض مختلف (hosting، production services، imagery...).

    Overview

    الأفكار الأساسية في الصفحة:

    • ArcGIS Server بيتوسع من deployment صغير على machine واحدة لحد deployment كبير على machines كتير.
    • تقدر تبدأ بتركيب كل الـ components على machine واحدة وانت بتبني الـ site، وبعدين تضيف ArcGIS Server machines للإنتاج أو لدعم مستخدمين أكتر.
    • الـ site ممكن يتكامل مع البنية الموجودة في الـ IT عندك: web server بتاعك، database، وأي identity providers خاصة بالمؤسسة.
    • إعدادات الـ high availability بتدعم العمليات الحرجة.
    • الـ Enterprise deployment الواحد ممكن يضم أكتر من ArcGIS Server site، كل واحد له غرض.

    والصفحة بتختم بملحوظة مهمة: السيناريوهات دي إرشادات (guidelines). تقدر تستخدمها زي ما هي أو تعدّلها حسب احتياجك وhardware بتاعك.

    Terms: المصطلحات اللي لازم تفهمها

    Site
    واحد أو أكتر من ArcGIS Server machines + ArcGIS Web Adaptor. الـ components ممكن تتوزع على machines لقوة حوسبة وredundancy أكتر. كل الـ machines بتشارك على قدم المساواة (مفيش master).
    ArcGIS Server
    الـ component الرئيسي اللي بيعالج طلبات الـ GIS web services: توليد خرائط، تشغيل أدوات، تقديم imagery، وعمليات تانية.
    ArcGIS Web Adaptor
    بيعمل نقطة دخول ويب للـ site، وبيتكامل مع الـ web server، وبيوزّع الطلبات الواردة على ArcGIS Server machines. توصية Esri: استخدمه مع الـ server site إلا لو عندك third-party load balancing بيقدر يقوم بمسؤولياته.
    Reverse proxy server (اختياري، طرف تالت)
    بيقعد بين الـ clients والـ servers وبيستقبل الطلبات نيابة عن الـ client. أغلب المؤسسات بتستخدم واحد علشان الـ site ما يتعرّضش مباشرة للـ clients.
    Network load balancer (NLB) (اختياري، طرف تالت)
    بيوزّع الـ network traffic على مجموعة hosts لتحسين الـ scalability والـ availability. غالبًا بيكتشف وقوع machine ويحوّل الـ traffic للسليمة.
    Server directories
    بتخزن الملفات اللي بتدعم الـ services: map caches، search indexes، ونتايج geoprocessing jobs.
    Configuration store
    directory بيحتوي إعدادات الـ site (زي قايمة الـ machines المشاركة). لازم يكون متاح علشان الـ site يشتغل. تقدر تحدد مكانه من Manager.
    Data
    الداتا اللي بتدعم الـ services: feature classes، أدوات، imagery، locators.
    اربط المصطلحات بالـ Enterprise اللي عرفته

    الـ Web Adaptor والـ reverse proxy هما بالظبط "الباب الأمامي" اللي اتكلمنا عنه في صفحة الـ components. والـ configuration store هو "ذاكرة الـ site": لو راح، الـ site مش عارف إيه machines اللي فيه ولا إعداداته. ده ليه أهمية خاصة في صفحات الـ multimachine.

    1. الـ site متعرّض للإنترنت؟

      لو أيوه، لازم Web Adaptor أو reverse proxy، وعزل ورا firewall. روح لـ single + proxy أو multi.

    2. محتاج HA أو سعة أفقية؟

      لو أيوه، multiple machine. لو لأ، single machine كفاية وأبسط.

    3. محتاج web-tier authentication (IWA، PKI، SSO)؟

      لو أيوه، لازم تستخدم Web Adaptor مش load balancer طرف تالت.

    4. عندك load balancer معتمد في المؤسسة بيعمل health checks؟

      لو أيوه، وما محتاجش web-tier auth، ممكن multi + load balancer.

    5. هتعمل federate مع portal؟

      لو أيوه ومحتاج HA، ما تستخدمش single-machine HA؛ استخدم multiple machine.

    سيناريو واقعي (مثال توضيحي): نفس المشروع في 3 مراحل

    مشروع بنية GIS لبرنامج طرق: مرحلة التجربة: machine واحدة VM بـ Web Adaptor، الفريق بيجرب النشر والـ dashboards. مرحلة الإطلاق الداخلي: نفس الـ machine بس مع قفل الـ admin على 6443 وتقييد IP، لأن 80 مستخدم داخلي بقوا يعتمدوا عليها. مرحلة التوسع: الحمل زاد وطلبوا HA، فاتنقلوا لـ multiple machine بـ 3 machines وnetwork share للـ config store والـ directories، وWeb Adaptor على IIS بنفس الـ URL. الـ URL ما اتغيّرش للمستخدمين لأنهم كانوا دايمًا بيوصلوا من خلال DNS alias.

    Key takeaways

    • الـ site = ArcGIS Server machines + Web Adaptor، وكل الـ machines متساوية.
    • تقدر تبدأ على machine واحدة وتوسّع بإضافة machines.
    • الـ configuration store لازم يكون متاح دايمًا؛ والـ server directories بتحمل الـ caches ونتايج الـ jobs.
    • أربع سيناريوهات رئيسية، وSingle-machine HA مش بيتعمله federate مع portal.
    • الـ web-tier authentication بيحتاج Web Adaptor، ومش متاح مع load balancer طرف تالت.
    • السيناريوهات إرشادات، تعدّلها حسب احتياجك.
    Deployment scenarios

    Single-machine deployment

    site على machine واحدة

    أبسط شكل لـ ArcGIS Server site: machine واحدة. Esri بتوصفه بإنه سهل في الإعداد والصيانة والـ upgrade، ومناسب لـ sandbox للتطوير والاختبار، وكمان صالح (وأحيانًا مثالي) لبعض بيئات الـ production. والـ site ممكن يتعمل له federate مع ArcGIS Enterprise أو يشتغل stand-alone. الصفحة دي شرح كامل للصفحة الرسمية "Single-machine deployment" مع التركيز على قرارات Windows: مكان الـ config-store، والحساب اللي بيشغّل الـ server، وماذا يحصل لو ما استخدمتش Web Adaptor.

    ArcGIS Server account

    الـ machine الواحدة بتشتغل تحت ArcGIS Server account، وده ممكن يكون local operating system account أو domain account. الاختيار بيتأثر بسياسة الأمان وبمكان الداتا اللي هيوصلها الحساب.

    على Windows

    في single machine غالبًا الحساب المحلي كفاية لأن كل حاجة محلية. لكن لو الداتا أو قاعدة البيانات على شبكة، الـ domain account بيسهّل منح الصلاحيات على الموارد دي. قرر بدري؛ تغيير الحساب بعد التركيب بيحتاج إعادة ضبط صلاحيات.

    Server directories and configuration store

    النقطة الأهم في الصفحة: عشان فيه machine واحدة بس، الـ server directories والـ configuration store لازم يبقوا على local disk، مش على network share.

    النظامصح (محلي)غلط (شبكة)
    WindowsC:\arcgisserver\config-store\\share\config-store
    Linux/opt/arcgis/server/usr/config-store/net/config-store

    ليه؟ الأسباب في الصفحة:

    • الـ local storage أداؤه أحسن وبيقلل الاعتماد على storage بعيد.
    • للـ cached map and image services استخدم volumes محلية أو direct-attached أو SAN مخصصة. استرجاع cache tiles من network share مكلف.
    • الـ cloud storage ممكن يستضيف بعض أو كل الـ server directories. لو الـ site on-premises (physical) خلّي الـ directories on-premises، والاستثناء هو cache directory اللي ممكن يكون على الـ cloud. ولو الـ site نفسه على cloud فاستخدم cloud storage للـ directories.
    سيناريو واقعي (مثال توضيحي): بطء الـ tiles

    فريق نشر basemap مخزّن (cached) لشبكة طرق على site وحط الـ cache directory على network share "علشان يتشارك". النتيجة: الخريطة بتتحمل ببطء بالرغم إن السيرفر قوي، لأن كل tile بيتقرأ عبر الشبكة. نقل الـ cache لـ local SSD على نفس الـ machine حل المشكلة من غير ما يتغير أي حاجة تانية.

    ArcGIS Web Adaptor

    المثال في الصفحة بيستخدم Web Adaptor، لكن ممكن تستخدم reverse proxy من طرف تالت بدله.

    • الـ clients بيستخدموا شكل الـ URL: https://gisserver.example.com/server.
    • الـ Web Adaptor بيحوّل الطلبات لـ server site machine على port 6443.
    • الوصول الإداري المباشر على 6443 يفضل متاح إلا لو عطّلته.
    • من الإصدار 10.7، ArcGIS Server بيفرض HTTPS افتراضيًا، وEsri بتوصي تفضّل كده (ممكن تفعّل HTTP لو ضروري).

    لو ما استخدمتش Web Adaptor ولا reverse proxy

    الصفحة بتحدد تلات مشاكل:

    Services مش على standard port
    التطبيقات عادةً بتتوقع HTTPS على 443، لكن ArcGIS Server بيستخدم 6443. الـ 443 يحتاج Web Adaptor أو reverse proxy. الوصول المباشر عبر 6443 ممكن يشتغل على intranet.
    Administrative endpoints مكشوفة
    ArcGIS Server Manager والـ Administrator Directory بيشاركوا نفس port الـ services (6443). العمليات الإدارية بتحتاج credentials، لكن حجب الوصول العام best practice خصوصًا للسيرفرات المتصلة بالإنترنت. تقدر تقيّد الوصول بالـ IP عن طريق عملية Update Security Configuration في الـ REST API.
    مفيش web-tier authentication
    PKI client certificates وIntegrated Windows Authentication وSSO بتحتاج Web Adaptor. من غيره الـ site بيستخدم token-based authentication بتاع Esri، مع إمكانية ربط بـ identity stores زي LDAP أو Windows Active Directory.

    Data

    • الداتا الملفية (file geodatabases، images، shapefiles) خزّنها محليًا لأفضل أداء.
    • الـ databases حطها على server مخصص.

    مثلاً: الـ enterprise geodatabase بتاعتك (SQL Server أو PostgreSQL) على سيرفر database لوحده، والـ ArcGIS Server بيتصل بيها. وملفات الـ file geodatabase والـ rasters على disk محلي على الـ machine الواحدة.

    Summary: ميزات وعيوب

    الإعداد ده بسيط في التركيب والـ upgrade. نموذجي للـ development والاختبار، وصالح للـ production خصوصًا على الـ intranet اللي احتياجاته الأمنية متوسطة. البيئات الأعلى أمانًا لازم تستخدم Web Adaptor أو reverse proxy. وهو مناسب جدًا لـ production cached map and image services اللي محتاجة أقصى throughput، وفي الـ deployments الكبيرة ممكن single-machine site يستضيف الـ cached services جنب sites تانية بتستضيف services تانية.

    Availability

    فيه GIS server واحد، فهو single point of failure. أي عطل hardware أو software بيوقف الخدمة.

    Scalability

    الـ config store والـ directories محلية، فمش هتقدر تضيف GIS servers تانية. التوسع vertical بس: تزوّد cores على نفس السيرفر.

    Advantages

    سهل في التركيب والصيانة والـ upgrade. أداء عالي لأن المسارات محلية، فمثالي للـ cached map وimage services.

    Disadvantages

    الأمان (Manager والـ Admin على نفس port)، منافذ غير قياسية، مفيش web-tier auth من غير Web Adaptor، ومفيش HA.

    تقوية الأمان من غير Web Adaptor: allowedAdminAccessIPs

    الصفحة بتقترح تقييد الوصول الإداري بالـ IP باستخدام الخاصية allowedAdminAccessIPs في الـ Security Configuration (عن طريق Update Security Configuration في الـ REST API). ده بيخلي بس عناوين محددة (مثلاً سيرفر الـ admin أو شبكة الـ IT) توصل للـ Administrator Directory. للعزل الكامل: اعمل routing للـ traffic عبر reverse proxy أو Web Adaptor.

    سيناريو واقعي (مثال توضيحي): lab الـ Windows بتاعك

    بتجهز lab على Windows Server VM. ركّب ArcGIS Server وWeb Adaptor على نفس الـ VM، وخلّي الـ config-store على C:\arcgisserver\config-store، واستخدم الـ domain أو local account حسب الـ VM. جرّب نشر خدمة من ArcGIS Pro، وجرب تفتح https://gisserver.example.com:6443/arcgis/manager مباشرة وبعدين عبر الـ Web Adaptor، وشوف الفرق بنفسك في الـ ports والـ URLs. ده أسرع تمرين لفهم الصفحة دي.

    Key takeaways

    • single machine = أبسط وأسرع، مناسب لـ dev/test وبعض الـ production.
    • الـ config-store والـ directories محلية (مثلاً C:\arcgisserver\config-store)، مش network share.
    • الـ cache tiles من network share مكلفة؛ الـ cache directory هو الاستثناء اللي يتحمل cloud.
    • من غير Web Adaptor/proxy: port 6443، admin مكشوف، ومفيش web-tier auth (IWA/PKI/SSO).
    • HTTPS مفروض افتراضيًا من 10.7.
    • مفيش HA، والتوسع vertical بس.

    Single machine with reverse proxy

    machine واحدة مع reverse proxy

    لو الـ single-machine site بتاعك هيتفتح من الإنترنت أو حتى من شبكات مش مضمونة، محتاج حاجة بين الـ clients وبين ArcGIS Server: reverse proxy. Esri بتقول إنه بيشتغل كوسيط لطلبات الـ clients على موارد الـ site وبيضيف مميزات أمان. الصفحة دي شرح لصفحة "Single-machine deployment with reverse proxy server": متى تستخدمه، وبيدخل في الـ architecture إزاي، ومميزاته وعيوبه، والفرق بين Web Adaptor وأي reverse proxy من طرف تالت.

    Introduction

    • الـ reverse proxy هو وسيط لطلبات الـ clients على موارد الـ ArcGIS Server site، وبيضيف مميزات أمان.
    • الـ ArcGIS Web Adaptor هو component بيشتغل في أغلب الـ web application servers الشائعة. وreverse proxy web servers من طرف تالت هي بديل.
    • الـ Web Adaptor أو الـ proxy بيتركّب عادةً على web server machine منفصلة، لكن ممكن يتركّب على نفس machine الـ ArcGIS Server.
    • الـ clients مش بيحسوا بفرق بين الوصول المباشر للـ GIS services والوصول من خلال الـ proxy.

    أربع أسباب للمدير إنه يستخدم reverse proxy (هنشرحها واحد واحد):

    1. Standard ports

    الوصول للـ services عبر 443 بدل 6443.

    2. عزل الـ server

    تخبي ArcGIS Server ورا firewall المؤسسة.

    3. حجب الإدارة

    تمنع الوصول لـ Manager والـ Administrator Directory.

    4. مميزات الـ web server

    logging وcaching وauthentication بتاع الـ web server عندك.

    Access GIS services over standard ports

    من غير proxy الـ clients بيتصلوا مباشرة بـ ArcGIS Server، مثلاً https://gisserver.example.com:6443 لما HTTPS متظبط. والـ default ports بتاعت ArcGIS Server ما ينفعش تتغير. فلو عايز الـ clients يستخدموا port 443 القياسي، اعمل reverse proxy ووجّه الـ clients ليه.

    أمثلة على الـ web context URL للـ proxy من الصفحة: http://proxy.example.com/arcgis أو http://proxy.example.com/myGIS. (في الإنتاج استخدم HTTPS طبعًا؛ المثال في الصفحة كده.)

    Isolate ArcGIS Server behind your organization's firewall

    ده مُوصى بيه لما تنشر services وتطبيقات للعامة على الإنترنت. التدفق:

    1. الـ traffic الواصل من الإنترنت يعدّي على firewall بيحجب كل الـ ports ما عدا 443

      أي محاولة للوصول لـ 6443 أو أي port تاني من بره بتتقفل.

    2. الـ reverse proxy يستقبل الطلب

      الـ proxy قاعد في perimeter network (DMZ)، وده بيساعد في التحكم في الوصول للشبكة الداخلية.

    3. الـ proxy يوجّه الطلب لـ ArcGIS Server عبر firewall تاني على port 6443

      الـ firewall التاني بيسمح بس بـ traffic جاي من الـ proxy.

    4. الـ proxy يرجّع الـ response للـ client

      الـ client عمره ما اتصل مباشرة بالسيرفر.

    سيناريو واقعي (مثال توضيحي): نشر خريطة عامة

    جهة عايزة تنشر خريطة مشروع طريق للعامة. بدل ما تفتح 6443 على الإنترنت، الـ DMZ فيها IIS بـ Web Adaptor (أو reverse proxy)، والـ firewall الخارجي بيفتح 443 بس. السيرفر الفعلي في الشبكة الداخلية، ومحدش من بره يعرف اسمه ولا يوصله مباشرة. لو حد اخترق الـ DMZ، لسه محتاج يعدّي firewall تاني.

    Block administrative access to your site

    الـ proxy يقدر يحجب موارد معينة زي ArcGIS Server Manager وArcGIS Server Administrator Directory. الصفحة بتسمّي ده good practice خصوصًا للـ services المتعرضة للإنترنت.

    لو بتستخدمإزاي تحجب الإدارة
    ArcGIS Web Adaptorعطّل الـ administrative access من خطوات "Configure ArcGIS Web Adaptor with a server site".
    Reverse proxy طرف تالتارجع لـ documentation المنتج واحجب: proxy.domain.com/arcgis/manager/ (Manager) وproxy.domain.com/arcgis/admin/ (Administrator Directory).
    الحجب على مستوى الـ proxy بس

    الحجب بيطبّق من خلال الـ proxy فقط. الوصول الإداري لسه متاح لو اتصلت مباشرة بـ ArcGIS Server على port 6443. لذلك لازم تتحكم في الوصول للـ ports دي بالـ firewalls كمان، مش بس بالـ proxy.

    Leverage features in your own web server

    لما تشارك الـ GIS services من خلال الـ proxy، تقدر تستفيد من مميزات الـ web server بتاعك: الـ logging والـ caching والـ security.

    Web-tier authentication
    افتراضيًا ArcGIS Server بيستخدم token-based authentication (اسمه كمان GIS-tier authentication). الـ web-tier authentication بيفوّض الـ authentication للـ web server بتاعك، فيدعم HTTP basic وclient certificates وطرق قياسية تانية، ومنها Integrated Windows Authentication مع Microsoft IIS. ده بيحتاج ArcGIS Web Adaptor؛ الـ reverse proxy الطرف تالت ما بيدعمهوش.
    Logging
    logs الـ ArcGIS Server بتغطي تفاصيل الـ service (العمليات المستدعاة، أوقات التنفيذ، التحذيرات، الأخطاء). logs الـ web server بتضيف: IP الـ client، الـ user agent، الـ referrer.
    مميزات تانية
    الـ web servers تقدر تفلتر الطلبات الواردة، وتحجب IP addresses أو domain names معينة، وتتحكم بدقة في الـ requests والـ responses.
    سيناريو واقعي (مثال توضيحي): ليه الـ logs مهمة

    فجأة الـ service بقت بطيئة. logs ArcGIS Server بتقولك إن عملية query معينة بتاخد 40 ثانية، لكن ما بتقولكش مين بيطلبها. logs الـ IIS بتقولك إن نفس الـ IP بيبعت مئات الطلبات في الدقيقة. الاتنين مع بعض يكشفوا إنه script أحدهم شغال بدون حد أقصى. من غير الـ proxy ما كانش عندك الـ IP.

    أكتر من reverse proxy لنفس الـ site

    الصفحة بتقول إن الـ site ممكن يستخدم أكتر من reverse proxy. مثلاً: اتنين web adaptors لفصل الـ services العامة (public) عن الخاصة (private) في site بيستخدم Windows Active Directory users. (الصفحة بتحيل لموضوع "Supporting a mix of public and private services" في documentation الـ ArcGIS Server المستقل.)

    مثال على Windows: Web Adaptor واحد اسمه public بدون authentication للـ services المفتوحة، وWeb Adaptor تاني اسمه internal بـ Integrated Windows Authentication للموظفين. نفس الـ site، بوابتين.

    Summary

    • Web Adaptor أو reverse proxy طرف تالت بيكمّل الـ single-machine deployment بإضافة أمان.
    • موصى بيه بشدة لو هتعرّض الـ site للإنترنت، وممكن تحتاجه حتى على الـ intranet حسب متطلبات الأمان.

    Advantages

    طبقة أمان إضافية فوق الـ single-machine deployment.

    Disadvantages

    الـ proxy بيضيف overhead على الطلبات، خصوصًا مع web-tier authentication على identity stores كبيرة أو معقدة (nested groups أو federated). ومش highly available: الـ ArcGIS Server machine والـ proxy الاتنين single points of failure.

    واجبات الـ proxy (حسب الصفحة)

    الصفحة ما بتحددش متطلبات برمجية رسمية، لكنها بتوصف واجبات الـ proxy:

    Key takeaways

    • الـ default ports بتاعت ArcGIS Server (زي 6443) ما ينفعش تتغير؛ للـ 443 محتاج proxy أو Web Adaptor.
    • الـ proxy في DMZ + firewall بيفتح 443 بس من بره، وfirewall تاني بيسمح 6443 من الـ proxy بس.
    • حجب Manager وAdmin على الـ proxy مش كفاية: لازم الـ firewalls تقفل 6443 من بره.
    • Web-tier authentication (IWA، client certificates) بيحتاج Web Adaptor، مش reverse proxy طرف تالت.
    • أكتر من web adaptor ممكن يفصل public عن private.
    • العيب: overhead ومفيش HA (الـ server والـ proxy single points of failure).

    Multiple machines with Web Adaptor

    أكتر من machine مع Web Adaptor

    لما machine واحدة ما بقتش كفاية (سعة أو availability)، بتنتقل لـ multiple-machine site: اتنين أو أكتر من ArcGIS Server machines بيشتغلوا كوحدة منطقية واحدة. الصفحة الرسمية "Multiple-machine deployment with ArcGIS Web Adaptor" بتشرح أبسط شكل ليه: pool من machines ورا ArcGIS Web Adaptor شغال على web application server بتاعك. الصفحة دي شرح كامل ليها، مع كل قرارات الـ Windows: الـ network share، الحساب، الـ opportunistic locking، وإزاي تعمل HA.

    Introduction

    الأفكار الأساسية:

    • الـ multiple-machine site بيخلّي اتنين أو أكتر من ArcGIS Server machines يشتغلوا كوحدة منطقية واحدة. المدير يقدر يضيف أو يشيل machines لتغيير قوة الحوسبة.
    • الـ site بيبسّط نشر وتحديث الـ services عبر الـ machines.
    متطلبات لازم تتحقق
    • كل ArcGIS Server في الـ site لازم يشتغل بنفس رقم الـ version.
    • كل ArcGIS Server لازم يتطبق عليه نفس الـ license.

    (ده بيتقاطع مع قاعدة الـ editions في صفحة الـ extensions: كل الـ machines على نفس الـ edition.)

    • أبسط configuration: pool من اتنين أو أكتر ArcGIS Server machines قدامهم ArcGIS Web Adaptor شغال على الـ web application server بتاعك.
    • كل الـ machines بتشارك configuration store واحد ومجموعة server directories واحدة. المدير يقدر يسجّل دخول على أي server من خلال ArcGIS Server Manager ويعمل تغييرات تتطبق على كل الـ machines.
    • النمط ده مناسب كمان للـ sites اللي بتتكامل مع طرق الـ authentication في الـ web tier بتاعة المؤسسة.
    تحذير أداء من الصفحة

    الـ network locations المشتركة للـ server directories والداتا ممكن تضر بالأداء. العوامل: عرض النطاق وثبات الشبكة، وopportunistic locking، وسرعة الـ network drive. والتأثير بيزيد تحت الحمل العالي. ولو على cloud، Esri بتوصي تخزّن الـ directories دي في cloud service.

    الـ opportunistic locking (oplocks) آلية في بروتوكول SMB على Windows بتخلي الـ client يعمل caching للملف محليًا. مع أكتر من machine بتكتب في نفس الـ config store والـ directories، ده ممكن يسبب تأخير أو سلوك غير متوقع، وده ليه Esri بتحيلك لصفحة Microsoft عنها. اتفق مع فريق الـ storage/Windows على إعدادات الـ share قبل الإنتاج.

    ArcGIS Server machines, server directories, and configuration store

    On-premises
    الـ deployment لازم يستخدم network location للـ server directories والـ configuration store، لأن كل الـ machines بتشاركهم. على Windows ده غالبًا UNC path زي \\fileserver\arcgisserver\config-store و\\fileserver\arcgisserver\directories.
    Cloud
    تخزين الداتا وملفات الإعداد في Amazon S3 buckets على AWS أو Blob Storage containers على Microsoft Azure. المزوّد هو اللي بيدير الـ availability ومواقع التخزين.
    ArcGIS Server account
    غالبًا domain account لأنه بيسهّل صلاحيات الوصول لموارد الشبكة. الحسابات المحلية مسموحة حسب سياسة الأمان. الحساب (محلي أو domain) محتاج write access على الـ network share اللي فيه الـ config store والـ server directories.
    على Windows: صلاحيات الـ share

    أنشئ domain service account مخصص (مثلاً DOMAIN\svc_arcgis)، وامنحه Full control أو على الأقل Modify على الـ share وعلى الـ NTFS permissions للفولدرات. صلاحيات الـ Share والـ NTFS الاتنين لازم يسمحوا. أكتر خطأ شائع: الـ share سامح لكن الـ NTFS لا.

    Data

    • الداتا الملفية: استخدم موارد محلية على كل ArcGIS Server machine لو ممكن. الميزة: traffic شبكة أقل وأداء services أحسن. العيب: الداتا لازم تتكرر على كل server.
    • حجم الداتا ومعدل تحديثها هما اللي بيحددوا إذا النسخ المحلية عملية.
    • الـ databases: استخدم hardware مخصص، واحتفظ بطبقة الـ database منفصلة عن طبقة ArcGIS Server.
    سيناريو واقعي (مثال توضيحي): file geodatabase على 3 machines

    الفريق عنده file geodatabase بـ 8 GB بيتحدّث مرة في الشهر، وservices عالية الطلب. النسخ المحلية على الـ 3 machines منطقية: بتنسخها بـ script بعد كل تحديث. لو الـ geodatabase بتتحدّث كل ساعة، النسخ المحلية بتبقى كابوس، والحل الصح يكون enterprise geodatabase على database server مخصص (وده يتماشى مع نصيحة الصفحة).

    Web Adaptor

    مسار الـ traffic
    طلبات الـ clients ما بتتصلش مباشرة بـ ArcGIS Server. بتعدّي على Web Adaptor، اللي بيضيف أمان ويحسّن المرونة.
    الوصول الإداري
    استخدام نفس القناة للاستخدام والإدارة غير موصى بيه. الإدارة بتتحدد عادةً بأجزاء شبكة أو machines تقدر توصل لـ ArcGIS Server مباشرة على port 6443. استخدم الخاصية allowedAdminAccessIPs في الـ security configuration لتحديد الـ IP addresses اللي تقدر توصل للـ Administrator Directory.
    إيه اللي الـ Web Adaptor بيعمله
    بيشتغل كـ reverse proxy قدام ArcGIS Server machines (مركّب على الـ web server بتاعك)، وبيدمج ArcGIS Server مع طرق الـ authentication القياسية في المؤسسة، وبيشتغل مع web-tier authentication (ArcGIS Server بيفوّض الـ authentication للـ web server بدل GIS-tier authentication). الـ web servers المدعومة في قائمة system requirements الخاصة بالـ Web Adaptor.
    أكتر من Web Adaptor
    تقدر تضبط أكتر من واحد لدعم طرق authentication مختلفة (مثلاً public وprivate).
    Load balancing
    بيوزّع الطلبات على الـ pool بنظام round-robin، وبيكتشف تلقائيًا ArcGIS Server machines الجديدة المضافة للـ site، وبيوقف التوجيه لأي machine مش متاحة أو اتشالت من الـ site.
    سيناريو واقعي (مثال توضيحي): أضف machine من غير ما تعمل أي حاجة للـ Web Adaptor

    الاستخدام زاد وقررت تضيف ArcGIS Server رابع للـ site. بعد ما تضيفه، الـ Web Adaptor بيلاقيه تلقائيًا ويبدأ يبعت له طلبات. ما بتحتاجش تعدّل أي إعداد في IIS. وبنفس الطريقة، لو machine وقعت، الـ Web Adaptor بيوقف الطلبات ليها لوحده.

    High availability considerations

    1. طبقة الـ Web Adaptor

      أضف redundancy بضبط أكتر من Web Adaptor (مثلاً على IIS servers مختلفة)، وكل واحد منهم بيعمل round-robin لكل الـ ArcGIS Server machines. وبعدها محتاج طريقة توزّع بيها على الـ Web Adaptors نفسها (DNS أو load balancer قدامهم).

    2. إزالة single points of failure في الداتا والـ config store والـ directories

      في الـ cloud استخدم cloud service للـ system directories. الداتا الملفية كررها على الـ machines لو ممكن (الحجم وتكرار التغيير ممكن يخليها غير عملية). والـ network shares اللي فيها داتا ملفية: ظبط الـ storage نفسه للـ HA.

    3. الـ databases

      الـ databases المدعومة من ArcGIS بتوفر خيارات HA (clustering وغيره)؛ الصفحة بتحيل لـ documentation الـ database.

    4. الـ config store والـ server directories (غير cloud)

      لازم دايمًا يكونوا على network share. ظبط الطبقة دي للـ HA لو محتاج. على Windows ده معناه غالبًا file server clustered أو storage مكرر حسب بنية المؤسسة (ده اقتراح منا؛ الصفحة بتقول بس إن الطبقة دي لازم تتأمن).

    النقطة اللي بتتنسى

    لو عملت 3 ArcGIS Server machines وعدة Web Adaptors وسبت الـ file share واحد على server واحد، فالـ HA بتاعك وهمي: لو الـ share وقع، الـ site كله وقع، لأن الـ configuration store "لازم يكون متاح علشان الـ site يشتغل".

    متى تستخدم النمط ده؟

    مناسب لمامش مناسب لما
    محتاج سعة أفقية وإضافة machines بسهولةمش عندك network share سريع ومستقر
    محتاج web-tier authentication (مثلاً IWA مع Active Directory)عندك load balancer معتمد وما محتاجش web-tier auth (شوف الصفحة اللي بعدها)

    Checklist لـ Windows

    Key takeaways

    • الـ multi-machine site: كل الـ machines نفس الـ version ونفس الـ license، وبتشارك config store وdirectories واحدة.
    • على on-premises الـ share إلزامي؛ على cloud استخدم S3 أو Azure Blob.
    • الـ network share ممكن يضر بالأداء (bandwidth، oplocks، سرعة الـ drive).
    • الـ Web Adaptor بيعمل round-robin ويكتشف الـ machines تلقائيًا، وبيدعم web-tier authentication.
    • لـ HA: Web Adaptors متعددة + share محمي + database HA. الـ config store لازم يفضل متاح دايمًا.
    • الإدارة بتتحدد بالـ IP عن طريق allowedAdminAccessIPs.
    Deployment scenarios

    Multiple machines with load balancer

    أكتر من machine مع load balancer

    نفس فكرة الـ multiple-machine site، لكن بدل ArcGIS Web Adaptor بتحط reverse proxy أو network load balancer من طرف تالت قدام الـ pool. ده الخيار الطبيعي لمؤسسات عندها load balancer معتمد أصلاً (F5، NGINX، HAProxy، أو load balancer بتاع cloud). الصفحة الرسمية "Multiple-machine deployment with third-party load balancer" بتشرح الشكل ده وقيوده. أهم قيد: مفيش web-tier authentication. الصفحة دي شرح كامل ليها، وبتركز على اللي بيختلف عن صفحة الـ Web Adaptor.

    Introduction

    • الـ multiple-machine site بيجمع اتنين أو أكتر ArcGIS Server machines في وحدة منطقية بيديرها المدير مع بعض. تقدر تضيف أو تشيل machines، ونشر وتحديث الـ services عبر الـ machines أبسط.
    • متطلبات الـ version والـ license: كل machine لازم تشتغل بنفس ArcGIS Server version، ولازم يتطبق عليها نفس الـ license بالظبط.
    • النمط الشائع: reverse proxy أو network load balancer من طرف تالت قدام pool من ArcGIS Server machines.
    • موارد مشتركة: كل الـ machines بتشارك configuration store واحد ومجموعة server directories واحدة. تقدر تسجّل دخول على أي machine في Manager وتطبّق تغييرات على الـ site كله.
    • تحذير الأداء: الـ server directories والداتا على network locations مشتركة ممكن تبطّأ الـ services تحت الحمل. في الـ cloud استخدم cloud service لتخزينها.
    القيد الأهم

    الـ web-tier authentication مش متاح مع الـ configuration ده. لو محتاج IWA أو PKI client certificates أو SSO عن طريق الـ web tier، الصفحة بتوجّهك لـ multiple-machine deployment مع ArcGIS Web Adaptor.

    Machines, server directories, and configuration store

    نفس الصفحة اللي قبلها بالظبط في الجوهر:

    On-premises
    الـ server directories والـ configuration store لازم يكونوا على network location لأن كل الـ machines بتشاركهم.
    Cloud
    Amazon S3 buckets على AWS أو Blob Storage containers على Azure. المزوّد هو المسؤول عن الـ availability والإدارة.
    Service account
    غالبًا domain account لتسهيل صلاحيات موارد الشبكة، أو local account حسب سياسة الأمان. الحساب محتاج write access على الـ share اللي فيه الـ config store والـ directories.

    Data

    • الداتا الملفية: الأفضل تبقى محلية على كل machine (يعني تتكرر عبر الـ machines) علشان تقلل الـ network traffic وتحسّن الأداء.
    • حجم الداتا ومعدل تحديثها بيحددوا إذا النسخ المحلية عملية.
    • الـ databases: hardware مخصص، وطبقتها منفصلة عن طبقة ArcGIS Server.

    Third-party reverse proxy server or network load balancer

    الدور والـ architecture

    الـ clients ما بيتصلوش مباشرة بـ ArcGIS Server machines. بيتصلوا بطبقة وسطى بتضيف أمان وبتحسّن المرونة قدام الأعطال.

    الأمان والوصول الإداري

    • استخدام نفس القناة للاستخدام والإدارة غير موصى بيه.
    • المهام الإدارية عادةً بتتحدد بأجزاء شبكة أو machines تقدر توصل لـ ArcGIS Server مباشرة على port 6443.
    • لتقييد الوصول الإداري: ظبط الخاصية allowedAdminAccessIPs في الـ security configuration بتاع الـ server، فبس IPs معينة تقدر تتصل.
    • الـ proxy لازم يحجب النقاط الإدارية:
      • الـ Administrator Directory: https://gisserver.example.com:6443/arcgis/admin
      • ArcGIS Server Manager: https://gisserver.example.com:6443/arcgis/manager
    • أغلب الـ proxies الطرف تالت بتقدر تفلتر الطلبات حسب نمط الـ URL لتنفيذ الحجب ده.

    Load balancing

    الـ reverse proxy هو كمان الـ load balancer بتاع الـ site. وخوارزمية round-robin بسيطة كفاية. يعني ما تحتاجش sticky sessions أو خوارزميات معقدة (الصفحة ما بتغطيش sticky sessions أصلاً، لكنها بتقول إن round-robin البسيط كافي).

    Health checks

    لو الـ load balancer بيدعم health checks، استخدم Health Check REST API endpoint بتاع الـ site للتأكد إنه قادر يستقبل الطلبات. ده بيساعد تكتشف بسرعة أعطال الـ software أو الـ hardware.

    # مثال: فحص صحة machine من PowerShell (الشكل المعتاد للـ endpoint - راجع صفحة Health Check في REST API للإصدار بتاعك)
# CHANGE_ME: اسم السيرفر
$server = "gisserver1.example.com"
Invoke-RestMethod -Uri "https://$($server):6443/arcgis/rest/info/healthCheck?f=json"
# الناتج المتوقع عند الصحة: success = True
    ليه health check مهم هنا بالذات؟

    الـ Web Adaptor بيكتشف الـ machines وبيستبعد الواقعة من نفسه. أما load balancer طرف تالت فمش بيعرف حاجة عن ArcGIS: لازم أنت تقوله إزاي يحكم إن الـ machine سليمة. من غير health check، هيفضل يبعت طلبات لـ machine واقعة ومستخدمينك هيشوفوا أخطاء متقطعة.

    ملحوظة: عمق الـ URL (من غير Web Adaptor)

    اسم الـ context بتاع الـ load balancer ممكن يكون مستوى واحد بس:

    مدعوممش مدعوم
    https://lb.example.com/enterprisehttps://lb.example.com/myorg/enterprise
    سيناريو واقعي (مثال توضيحي): ليه المؤسسة اختارت الـ load balancer

    جهة عندها فريق network بيدير load balancer مركزي لكل التطبيقات، وبيرفض إن يتركّب IIS إضافي. محتاجين 3 ArcGIS Server machines لخدمات الـ mapping، وما عندهمش مستخدمين بحاجة web-tier authentication (الدخول بـ token والـ SAML على مستوى الـ portal). الاختيار منطقي: load balancer مع health check على الـ endpoint، وحجب /admin و/manager، وallowedAdminAccessIPs لشبكة الـ IT. ولو جه متطلب IWA بعدين، هيحتاجوا Web Adaptor على الأقل لجزء من الـ traffic.
